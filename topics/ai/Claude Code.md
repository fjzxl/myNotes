# Claude Code 使用心得（Agent 编程实战）

> 核心观点（2026-09 闪念，本篇由此展开）：现在我们用 Claude Code 等 AI Coding 工具编码，其实不再是把自然语言翻译成代码，而是在做**设计**——具体是三件更高级的事：**拆解问题、分配任务、组织多个智能体协作完成目标**。

## 1. 范式转变：从"写代码"到"做设计"

传统开发的单位是"行"：想清楚一行写一行。Agent 编程的单位是"任务"：把目标拆成可独立验证的子任务，描述清楚约束与验收标准，交给 agent 执行，自己负责**审查与集成**。

| 维度 | 传统编码 | Agent 编程 |
|------|---------|-----------|
| 产出物 | 代码 | 任务描述 + 验收标准 + 审查 |
| 核心技能 | 语言/框架熟练度 | 问题拆解、上下文供给、结果验证 |
| 时间去向 | 打字 | 思考结构、读 diff、跑测试 |
| 失败模式 | bug | agent 理解偏差、上下文缺失、方向跑偏 |

这个转变意味着：**描述问题的能力比背诵语法更重要**。一个约束写得完整的任务书（输入输出、边界条件、要改哪些文件、不许动哪些），远比纠正十次生成结果省时间。

## 2. 三件高级事

### 2.1 拆解问题

- 先问"这个问题由哪几个可独立验证的小块组成"，再动手；宁可拆得偏小，不要一锅端。
- 每个子任务应当有**机器可验证的完成信号**：测试通过、脚本输出、编译零错。没有验证手段的任务描述是不合格的。
- 依赖关系显式化：先做不依赖别人的，后做集成的。

### 2.2 分配任务

- 任务书要素：背景（为什么改）、范围（改哪些，明确排除项）、验收（怎么算完成）、参考（相关文件/接口/风格约定）。
- 把**不变的约束**（代码风格、目录结构、禁止行为）固化成项目级说明文件（AGENTS.md / CLAUDE.md 一类），一次说明，每次生效——重复口头交代是最大的浪费。
- 小步提交：每个子任务完成后立即审查落盘，错误发现得越早，回滚成本越低。

### 2.3 组织多智能体协作

常见拓扑：

- **主控-执行（orchestrator–worker）**：主 agent 拆解与集成，子 agent 各领一个子任务。适合模块边界清晰的改造。
- **串行流水线**：agent A 的产出（如方案）作为 agent B 的输入（如实现），适合"先设计后编码"。
- **并行扇出**：多个 agent 独立调研/搜索，汇总结论。适合信息收集类任务，互不干扰。
- **生成-评审**：一个写实现，一个只挑毛病（对着验收标准审 diff）。便宜且有效地压制"看起来对"。

要点：子 agent 之间通常**不共享记忆**，每个任务的上下文要在任务书里自包含；主 agent 的职责是衔接集成点，而不是指望它们自己商量。

## 3. 实践清单

- [ ] 动手前写清目标与验收标准，而不是"帮我优化一下"
- [ ] 大任务先让 agent 出计划，人审计划再放行执行
- [ ] 每步产出可运行、可测试，禁止"一口气改完再看"
- [ ] diff 逐行审：agent 写的每一行都是"别人的代码"
- [ ] 把项目约定沉淀到 AGENTS.md，而不是每次重复交代
- [ ] 危险操作（删除、强推、覆盖）永远人工确认

## 4. 易踩的坑

- **上下文饥饿**：长会话后期 agent 忘掉早期约定。对策：关键约束写进项目说明文件；新会话开始时主动给出背景摘要。
- **表面完成**：代码"看起来对"但没跑过测试。对策：验收标准必须包含执行证据（测试输出、命令结果）。
- **过度自主**：放任 agent 连环修改无关文件。对策：任务书明确排除范围，改动后核对文件清单。
- **用 agent 逃避理解**：review 时只看"能不能跑"。长期看，不理解的部分终会在调试时还债——审查也是学习。
